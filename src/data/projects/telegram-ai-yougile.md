## Проблема

Поручения в переписке приходится вручную превращать в задачи: выделять действие, сохранять контекст и переносить данные в таск-трекер. При повторном переносе легко получить дубли.

## Бизнес-применение

Сценарий предназначен для маркетинговой команды: участник отвечает командой **/task** на сообщение с поручением, а workflow подготавливает структурированную карточку для YouGile. Возможная польза — меньше ручного переноса и сохранение связи с исходной перепиской. Экономия времени и результаты работы команды не измерены.

## Реализация

**Telegram → команда /task → проверка доступа и контекста → поиск дубля → LLM и JSON Schema → проверка ответа → YouGile API → подтверждение или сообщение об ошибке.**

В предоставленном экспорте n8n — **35 узлов**, включая служебные заметки. Реализация использует Telegram Bot API, HTTP-запросы к LLM, JSON Schema, JavaScript в Code-узлах и YouGile REST API.

- Команда обрабатывается только как ответ на сообщение; можно добавить уточнение после /task. Проверяются разрешённый чат и список пользователей.
- LLM получает текст поручения и уточнение, возвращает название, описание, направление, приоритет, имя исполнителя, срок и список недостающих сведений. Неопределённые данные по инструкции не должны выдумываться.
- Задан строгий JSON-контракт и дополнительная проверка ответа в Code-узле. Некорректный ответ направляется в ветку ошибки или ограниченного повтора.
- Доска и входящая колонка ищутся по настройкам. Поиск дубля проверяет маркер исходного сообщения в последних задачах; запрос создания содержит idempotencyKey.
- Для сетевых сбоев, 429 и 5xx предусмотрены ограниченные повторы с паузой; ошибки доступа 401/403 повторно не отправляются автоматически.

## Мой вклад

Работаю над персональной автоматизацией для сценария «поручение в переписке → задача». Подтверждающие материалы проекта — workflow n8n и инструкция настройки. Распределение авторства отдельных Code-узлов и результаты моих запусков в живом окружении в этих материалах отдельно не зафиксированы, поэтому они не заявляются как подтверждённые достижения.

## Что подтверждено

Экспорт читается как корректный JSON, содержит 35 узлов и все указанные связи. В нём workflow отмечен как неактивный, привязки credentials удалены. Выполнены **32 локальные проверки** на синтетических данных: разбор команды, доступ, обработка JSON, ветки ошибок и подготовка запросов.

Это проверки отдельных Code-узлов с подставленными данными. Они не заменяют импорт и выполнение workflow в n8n и не подтверждают работу внешних сервисов.

## Ограничения

- Рабочий production-запуск не подтверждён. В рамках проверки не выполнялись импорт, активация, запросы к Telegram/LLM/YouGile и создание реальных задач.
- Выявлен риск состояния циклов: обработчики используют .first() без номера запуска. Перед активацией нужно проверить переходы между шагами и повторы в целевой версии n8n.
- Исполнитель, срок и приоритет записываются в описание. Поля назначения исполнителя и дедлайна YouGile автоматически не заполняются.
- Поиск дублей ограничен последними 3000 задачами; полная защита от дублей и параллельных запусков требует интеграционной проверки. Поддержка idempotencyKey есть в спецификации API, но здесь не проверялась живым запросом.
- Пустые настройки доступа снимают ограничения чата и пользователей; перед рабочим запуском их нужно явно заполнить.
- Для настройки нужен отдельный Telegram-бот. В портфолио доступна обезличенная сводка проверки; доступы и внутренняя конфигурация в неё не входят.

## Доказательства

[Обезличенный артефакт проверки workflow](/projects/yougile-workflow-verification.json) содержит область проверки, результаты и ограничения без доступов и внутренних идентификаторов.

Обложка — схема процесса, а не скриншот успешного запуска. Технический контракт YouGile сверён с [официальной спецификацией API](https://yougile.com/api/).
