## Сценарий

AI-суфлёр — Windows-приложение для поддержки устного ответа во время онлайн-разговора. Оно получает звук микрофона и системного выхода, показывает транскрипцию и готовит короткую формулировку с учётом последнего вопроса и фактов из PDF-резюме. Человек читает, проверяет и выбирает, как использовать подсказку.

## Основа и адаптация

Основа — [Ecoute, проект SevaSk](https://github.com/SevaSk/ecoute), опубликованный под MIT. В исследованной upstream-версии уже есть захват микрофона и Windows WASAPI loopback, очереди аудио, раздельные потоки You/Speaker, Whisper/faster-whisper и окно транскрипции на CustomTkinter.

Эта основа дала готовый путь «два аудиоканала → текст». В адаптированной версии работа сосредоточена на сценарии суфлёра: фильтрации реплик, поиске вопроса, контексте резюме, генерации ответа и интерфейсе для его чтения. Исходный аудиодвижок Ecoute не приписывается автору портфолио.

| Часть | Ecoute upstream | Адаптированная версия |
|---|---|---|
| Захват и транскрипция | Микрофон + системный звук, очереди, Whisper | Сохранён фундамент; изменены настройки захвата, ограничена очередь, добавлены остановка recorder и обработка ошибок |
| Локальная ASR | tiny.en | multilingual tiny, русский язык, VAD, beam_size=3 |
| Контекст ответа | Транскрипция | Очистка шума, дедупликация, выбор последнего вопроса, стабилизация |
| PDF и подсказка | В исследованном upstream main.py отсутствуют | Загрузка PDF, лексический подбор фрагментов, GPT-4o-mini |
| Интерфейс | Текст транскрипции и очистка | Две области: транскрипция / AI-ответ; закрепление, прозрачность, фокус, состояние окна |

Сравнение проведено по исходникам, а не по общим функциям продуктов с похожим названием.

## Как работает система

1. Микрофон и WASAPI loopback записывают фрагменты в отдельные очереди. Callback ограничивает очередь 40 фрагментами, удаляя старые при переполнении.
2. AudioTranscriber собирает фразы и получает текст через Whisper API либо локальный faster-whisper. Реплики помечаются You/Speaker и объединяются по времени, новые — первыми.
3. Из текста убираются известные шумовые фразы и похожие повторы, в том числе между каналами. Затем берётся последняя значимая реплика Speaker, похожая на вопрос.
4. Вопрос должен оставаться неизменным 1,35 секунды. Уже обработанный текст не отправляется повторно. Это задержка стабилизации, не измеренная общая latency приложения.
5. Из недавнего диалога и PDF собирается ограниченный контекст. GPT-4o-mini получает вопрос, историю и выбранные факты; prompt запрашивает 1–3 предложения для устного ответа.
6. Ответ выводится в интерфейс. Ошибка показывается пользователю; вариант ответа не является автоматически проверенным утверждением.

## Инженерный разбор

### Вопрос важнее очередной реплики

Транскрипция обновляет незавершённую фразу. Если отвечать на каждое изменение, подсказка появится слишком рано или будет многократно переписываться. Worker проверяет текст каждые 0,30 с, запоминает время последнего изменения и ждёт стабилизации. last_processed_speaker_line блокирует повтор для того же текста в текущем worker.

Это эвристика: вопрос распознаётся по знаку «?» и словесным маркерам. Нет модели определения намерения и гарантии, что каждая последняя реплика является правильным вопросом.

### Дедупликация и два канала

Для похожих реплик используется difflib.SequenceMatcher и нормализация текста. Основной порог сходства — 0,84, межканальный — 0,80. Это помогает убрать эхо и повтор распознанного фрагмента, но не является полноценной диаризацией по голосам или семантической памятью.

### PDF-контекст без векторной базы

Текст разбивается на фрагменты по 850 символов с перекрытием 160. Релевантность считается по пересечению частот токенов; добавляются бонусы за лексические маркеры. Обычно выбираются до четырёх фрагментов с ограничением 4500 символов. Для вопросов об опыте действует отдельная ветка с лимитом 7000 символов и началом документа.

При отсутствии совпадений выбираются первые фрагменты. Для вопроса об опыте начало PDF способно занять лимит до добавления релевантных частей. Это **лексический отбор контекста**, не векторный RAG, embeddings или обученный поиск.

### UI для чтения во время разговора

В коде есть закрепление поверх других окон, slider прозрачности, режим фокуса, скрывающий второстепенные панели, и сохранение геометрии окна. Отдельная область показывает AI-ответ. Эти функции подтверждены реализацией; настоящий screenshot Windows-окна в этом аудите не снимался.

## Демонстрация и проверки

Исследована приватная версия `78f5d60` и сопоставлена с Ecoute `ffdeac3`. Закрытый код и ссылка на приватный репозиторий не публикуются.

**11 изолированных проверок чистых функций** выполнены на искусственных данных: разбиение с overlap, нормализация, шум, вопрос/обычное утверждение, последний Speaker, межканальный дубль, лексический выбор PDF-контекста и fallback. Проверяемые функции извлечены через AST без импорта main.py: GUI, аудиоустройства, личный PDF и сеть не запускались.

| Синтетический вход | Проверенный результат |
|---|---|
| Одинаковый вопрос в You и Speaker | Сохранена одна Speaker-реплика |
| Новый Speaker и более старая реплика | Выбрана первая, то есть последняя по порядку транскрипта |
| Запрос «лимоны» к двум искусственным фрагментам | Выбран фрагмент с лексическим совпадением |
| Запрос без совпадений | Возвращаются первые фрагменты, а не выдуманное семантическое совпадение |

[Область проверки и результаты (технический JSON)](/projects/ai-prompter-brief.json).

Это подтверждает локальные алгоритмы, а не качество ASR, ответа модели или работу Windows-приложения целиком.

## Мой вклад

Определение пользовательских сценариев и требований к суфлёру; работа с контекстом и промптами, конфигурацией, проверкой и доработкой ответов; итерации адаптированной версии с AI-инструментами. Изменения включают собственный слой сценария ответа и UI поверх Ecoute. Ручное авторство исходного аудиодвижка не заявляется.

## Бизнес-применение

Подход показывает, как объединить сторонний open-source компонент, локальную обработку, документный контекст и LLM в прикладном интерфейсе. Возможная область — подготовка и поддержка рабочих разговоров с согласованным использованием контекста. Качество формулировок, экономия времени и бизнес-эффект пока не измерены.

## Границы и развитие

Код подтверждён, Windows runtime на этом Mac не проверен. Нужны проверка реальных устройств, безопасная запись интерфейса и отдельное тестирование задержки, устойчивости и качества подсказок.

В requirements.txt не перечислены все прямые импорты main.py (в частности, PyPDF2, python-dotenv, colorama, Pillow); чистую установку нужно проверить. Обращения worker к Tk-виджетам, поведение после очистки контекста и повторные ошибки API также требуют проверки. Prompt не заменяет отдельную проверку фактов; вопрос и PDF-контекст при генерации передаются провайдеру LLM. Перед демонстрацией нужны согласованный синтетический разговор и обезличенный документ.
